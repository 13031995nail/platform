# AGENTS.md

Инструкции для агентской работы в репозитории `tmobis.core`.

## Область действия

- Этот файл относится к git-репозиторию `src/tmobis.core`.
- Не путай его с возможным родительским репозиторием (например, `2234.platformdev`): перед изменениями всегда проверяй `git status --short --branch` именно в `src/tmobis.core`.
- Не коммить изменения родительского репозитория, `.yarn/install-state.gz`, `.lscache`, локальные логи и другие артефакты IDE/сборки: перед комитами проверяй `.gitignore`.

## Структура проекта

Данный репозиторий является монорепозиторием из разных пакетов на разных стеках:
- `src/core/backend` - бэкенд ядра платформы с базовыми абстракциями.
- `src/core/react` - React Native/Expo/Gluestack ядро платформы с базовыми абстракциями и компонентами.
- `src/periphery/tech` - технические модули: адаптеры, подсистемы, фреймворки, утилиты.
- `src/periphery/business` - бизнес модули предметных областей: сущности и операции над ними.
- `src/templates` - шаблоны и эталоны приложений, включая `expo-app` и `back-ef`.
- `src/tools` - внутренние инструменты монорепозитория.

## Базовые команды

- Установка зависимостей: `yarn install` из корня `src/tmobis.core`.
- Сборка React-ядра: `yarn workspace @tmobis/core build`.
- Запуск Expo-шаблона: `yarn workspace expo-app start:web`.
- Expo-шаблон ожидает backend по `http://localhost:5000` из `src/templates/expo-app/app.json`.
- Для .NET проверяй конкретный проект: `dotnet build <path-to-csproj>`. Не запускай полный solution build без необходимости.

Если после merge появилась белая страница в Expo, сначала проверь лог Metro. Частая причина - новые зависимости из `package.json` еще не установлены; выполни `yarn install` и перезапусти `start:web`.

## Версии инструментов

- Ориентируйся на актуальный блок `volta` в `package.json`.
- На момент написания используются Node `24.13.0` и Yarn `4.12.0`.
- Если README расходится с `package.json`, приоритет у `package.json`.

## Стиль и соглашения

- Соблюдай `.editorconfig`, в том числе: LF, UTF-8, финальная новая строка, 2 пробела по умолчанию, 4 пробела для C#.
- Соблюдай общепринятые правила кодирования: Roslyn для C#, правила TypeScript.
- Не форматируй соседний код без причины: минимизируй дифф и не меняй кавычки/пробелы, если это не часть задачи.
- Для TypeScript/React следуй существующим паттернам файла и соседних компонентов.
- При написании комментариев использовать отглагольные существительные, например, "Применение фильтра", "Установка значения".

## Общие паттерны

- Добавляй новые адаптеры, подсистемы, фреймворки, утилиты в соответствующий раздел `src/periphery/tech`.
    - Для бэкенда создавать папки `имяПроекта/module` - где будет расположен сам проект, и `имяПроекта/tests` - для тестов
    - Если необходимо создать и фронтенд, и бэкенд, то бэкенд помещается в папку `имяПроекта/backend/...`, фронтенд - `имяПроекта/frontend`

## Backend/.NET паттерны

- Для платформенных сервисов предпочитай DI-модули и существующие интерфейсы, а не прямое создание инфраструктурных объектов внутри методов.
- Пользуйся существующими в проекте абстракциями:
    - Каждый проект - модуль, необходимо в нем создавать `IModule` и регистрировать DI-сервисы через него
    - По возможности использовать паттерн медиатор на основе `IMessage` и `IMessageConsumer`
    - Для репозиториев и транзакций следуй существующим `IRepository`, `IRepositoryFactory` и паттернам конкретного модуля.
- Проверяй только затронутые `.csproj`, если полный build слишком дорогой или падает на несвязанных модулях.

## Git и коммиты

- Используй conventional commits.
- Сообщения обычно пишутся на русском, в нижнем регистре: `feat: добавить ...`, `fix: исправить ...`, `chore: синхронизировать ...`.
- Не делай `git reset --hard`, `git checkout --` или другие разрушительные операции без прямого запроса.
- Если идет merge/rebase, сначала проверь конфликтные файлы через `git status` и `rg "<<<<<<<|=======|>>>>>>>"`.
- После разрешения конфликтов проверяй `git diff --check`.

## Проверки перед ответом

- `git status --short --branch` в `src/tmobis.core`.
- Для frontend-задач: минимум targeted build или явное объяснение, почему build не является чистым сигналом.
- Для merge-конфликтов: отсутствие conflict markers и понятное объяснение, какие версии были объединены.
- Для runtime-проверки Expo: убедись, что порт `8081` свободен или явно останови старый `expo start --web` процесс.

## Проведение code review

### Подготовка

Перед анализом изменений:

1. Прочитать настоящий AGENTS.md.
2. Определить базовую ветку и получить полный diff.
3. Изучить документацию затрагиваемых подсистем.
4. Найти существующие аналоги реализации в проекте.
5. При необходимости проследить вызовы и зависимости за пределами diff.

Не следует делать выводы о поведении Платформы исключительно
по названиям классов, методов или интерфейсов.

### Документация

Начальные точки:

- `docs/README.md` — архитектурная документация.
- `docs/tech/modules.md` — модульность.
- `docs/tech/entities.md` — сущности и материализация.
- `src/core/backend/docs/entity-patterns.md` — проектирование сущностей.
- `INTEGRATION_GUIDE.md` — интеграционные соглашения.

Читать документы выборочно, исходя из затронутых подсистем.

Если документация описывает механизм, который может объяснять
подозрительный код, необходимо проверить этот механизм до
формирования замечания.

Документация описывает предполагаемый контракт, но не заменяет
проверку фактической реализации. При расхождении документации
и кода явно указывать расхождение.

### Проверка предполагаемых дефектов

Для каждого потенциального замечания:

1. Установить ожидаемое поведение.
2. Проверить документированный контракт.
3. Проследить фактический путь исполнения.
4. Проверить наследование, DI-регистрацию, адаптеры,
   fallback-механизмы и другие применимые расширения.
5. Сравнить поведение с базовой веткой.
6. Определить конкретный сценарий возникновения проблемы.
7. По возможности подтвердить дефект тестом или сборкой.

Если подтверждения недостаточно, обозначить замечание как
гипотезу или риск, а не как установленный дефект.

### Критерии замечаний

Разделять:

- Регрессии, внесённые рассматриваемыми изменениями.
- Новые дефекты в добавленной функциональности.
- Существовавшие ранее дефекты.
- Архитектурные риски.
- Необязательные улучшения и рефакторинг.

Не требовать исправления исторических проблем, если они не
усугубляются изменениями и не блокируют новую функциональность.

Не требовать реализации новых возможностей, выходящих за рамки
задачи, только потому, что они могли бы улучшить продукт.

Не требовать дополнительных защитных проверок, абстракций
и рефакторинга без конкретного обоснования их необходимости.

### Формат замечаний

Каждое замечание должно содержать:

- Приоритет (P0–P3).
- Файл и конкретное место.
- Описание проблемы.
- Сценарий воспроизведения или условия проявления.
- Ожидаемое и фактическое поведение.
- Связь с изменениями ветки.
- Предлагаемое минимальное исправление.
- Степень уверенности в выводе.

Если замечание касается неподтверждённого поведения,
отдельно указывать, что именно требуется проверить.

### Итог ревью

Сначала перечислять подтверждённые дефекты по убыванию
приоритета, затем неподтверждённые риски.

Исторические проблемы и необязательные улучшения
указывать отдельно, не смешивая с блокирующими замечаниями.

Критерий завершения — отсутствие подтверждённых дефектов
в рамках изменений, а не устранение всех потенциальных
недостатков проекта.
