# Шаблон проекта на Платформе

Данный репозиторий является шаблоном проекта на Платформе и состоит из разных примеров:
- Фронтенд на ember-flexberry 3.1
- Фронтенд на Next.js
- Бэкенд на Flexberry OData и .Net 10
- Сэмпл подключения Redis-кэша
- Мобильное приложение Android на Cordova
- Liquibase для миграций SQL скриптов в БД
- Скрипты деплоя Docker приложения через Ansible 

## Чек-лист оценки технологичности проекта

> Чек-лист позволяет оценить уровень использования командой проекта рекомендованных лучших практик по разработке.
Не всегда требуется стопроцентное соответствие всем лучшим практикам, иногда масштабы проекта и/или размеры команды делают бессмысленным внедрение ряда практик, однако в целом стоит стремиться к высокому уровню использования лучших практик.

### Работа с системой контроля версий
- [x] Используется git. \
*Это де-факто стандарт индустрии, а его модель ветвления и распределенная структура позволяет проще вести коллективную разработку.*

- [ ] Каждый коммит связан с одной или несколькими задачами, которые он затрагивает. \
*Это необходимо, чтобы можно было определить по фрагменту кода в рамках какой задачи он был создан и наоборот.*

- [ ] Сообщения к коммитам соответствует формату
```
Краткое наименование (не больше 72 символов)

Подробное описание изменений с возможностью
переносить слова и добавлять списки
1. 
2.
3.

#taskid
```
*Краткое наименование может полностью показаться в git log и в инструментах просмотра истории коммитов. Подробное описание позволяет зафиксировать для себя или коллег контекст и причины выбранной реализации, подводные камни и прочие детали. Указание идентификатора задачи автоматически связывает коммит с задачей в трекере задач.*

- [ ] Сообщения к коммитам содержат осмысленные описания, нет множества маленьких коммитов вида `fix` и т.п.

- [ ] Работа с ветками ведется в соответствии с некоторым описанным процессом, описание доступно всем разработчикам \
*Благодаря этому можно анализировать историю коммитов, опираясь на всем известные правила.*

- [x] Новая функциональность добавляется в основную ветку с использованием merge request \
*Это позволяет настроить политики на добавляемые в основную ветку изменения (необходимость ревью, прохождения билда и пр.) и не допустить попадания в основную ветку несоответствующего соглашениям команды кода*

### Чистота кода
- [ ] Нет закомментированного кода \
*Большие фрагменты закомментированного кода заставляют задумываться находится ли в коде что-то полезное и нужно ли этот код учитывать при работе*

- [x] MR проходят ревью кода \
*Ревью кода это один из этапов обеспечения качества кода. С помощью этого инструмента также можно обучать членов команды (как в роли авторов PR/MR, так и в роли ревьюеров), поддерживать представление об архитектуре и реализованных в коде механизмах, используемых подходах и практиках.*

- [ ] Используются линтеры/инструменты для контроля соблюдения стиля кодирования \
*Единый стиль кодирования, контролируемый автоматически, снижает когнитивную нагрузку на разработчика при чтении кода и помогает добиться совместного владения кодом, а за счет этого и возможности разным людям работать над одним кодом без необходимости переключаться между разными стилями кодирования*

- [ ] Используются git-хуки, не позволяющие закоммитить или запушить код, не проходящий проверки линтеров \
*Это позволяет быстро обнаружить и исправить ошибки, не запуская серверный билд, который упадет из-за ошибок форматирования*

### CI/CD
- [x] Настроен серверный билд для PR/MR \
*Это позволяет проверить, что предложенные изменения не нарушают стиль кодирования, собираются и проходят тесты*

- [x] Настроен серверный билд/релиз для развертывания всех разрабатываемых сервисов проекта на тестовый стенд \
*Это позволяет "чистую" сборку проекта, независимую от локального окружения конкретного разработчика, и убирает необходимость ручных действий для развертывания новой версии для тестирования*

- [ ] Настроен серверный билд/релиз для сборки всех разрабатываемых сервисов проекта для прода \
*Может быть как просто сборка в конфигурации для прода, так и полное развертывание на прод. Позволяет упорядочить и ускорить развертывание на прод, избавиться от возможных зависимостей от локального окружения разработчика.*

- [ ] Серверный билд запускает модульные тесты

- [ ] Серверный билд запускает интеграционные тесты

- [ ] Серверный билд запускает тесты пользовательского интерфейса (приемочные)

- [ ] Серверный билд проверяет корректность и идемпотентность скриптов изменения БД

- [x] Серверные билды используют секретные переменные при тестировании и развертывании сервисов \
*CI/CD-инструменты позволяют безопасно работать с секретами и паролями и не раскрывать их всем, кто имеет доступ к самому инструменту*

### Тестирование
- [ ] Есть модульные тесты бекенда \
*Позволяют тестировать корректность реализации алгоритмов и бизнес-правил*

- [ ] Есть интеграционные тесты бекенда \
*Позволяют тестировать корректность реализации алгоритмов и бизнес-правил, затрагивающих несколько сервисов и/или БД*

- [ ] Есть модульные тесты фронтенда \
*Позволяют тестировать корректность реализации алгоритмов и бизнес-правил на фронтенде*

- [ ] Есть интеграционные тесты фронтенда \
*Позволяют тестировать корректность работы отдельных компонентов*

- [ ] Есть тесты пользовательского интерфейса (приемочные) \
*Позволяют тестировать корректность реализации визуального поведения приложения*

- [ ] Есть тесты производительности \
*Можно проверять как соответствие приложения предъявляемым нефункциональным требованиям, так и отслеживать динамику изменения показаний, чтобы обнаруживать изменения, приводящие к деградации производительности. Следует выполнять в независимом окружении или с осторожностью, чтобы не помешать другим проектам*

- [ ] При исправлении ошибки, найденной на проде, создается тест, который ее воспроизводит \
*Позволяет в будущем не столкнуться с регрессией, что может куда больше раздражать пользователей, чем новые баги*

### Процесс разработки
- [ ] Регулярно проводятся ретроспективы для улучшения процесса разработки \
*В ходе ретроспективы можно переключить внимание и посмотреть на применяемые процессы отвлеченным взглядом, обсудить проблемы и подходы, которые можно улучшить, запланировать перечень изменений процессов для исправления неудобств*

- [ ] Отдельные механизмы и подсистемы проекта подвергаются предварительному проектированию и описанию, например в форме RFC \
*Если механизм крупный и важный, необходимо основательно подойти к его разработке, выявить нефункциональные требования и разработать архитектуру с их учетом. В противном случае можно столкнуться с неразрешимыми проблемами при внедрении и/или чрезмерными трудозатратами на поддержку неправильно спроектированного механизма*

- [x] Пароли и секреты хранятся в менеджере паролей с разделением прав доступа \
*Неконтролируемый доступ к паролям несет за собой высокие риски, которых проще избегать, чем бороться с последствиями их срабатывания*

- [ ] В процессе решения инцидентов на проде применяется практика написания пост-мортемов \
*Это позволяет лучше разобраться в произошедшем, а также запланировать конкретные меры по недопущению подобных инцидентов в будущем*

### Бекапы
- [x] Есть бекапы критически важной информации

- [x] Бекап хранится на другом диске, нежели основные данные

- [ ] Механизм бекапов регулярно проверяется на корректную работу \
*Лучше всего проверять возможность восстановления данных и корректной работы после этого*

### Работа с БД
- [ ] Для доступа к БД сервисов используются отдельные разные учетки без прав администрирования сервера \
*При утечке одной из учеток остальные БД останутся нескомпрометированными*

- [ ] Скрипты изменения БД являются идемпотентными \
*За счет этого их можно применять несколько раз как вручную, так и в автоматическом режиме*

- [x] В БД настроен сбор статистики и регулярные задачи обслуживания \
*Сбор статистики позволяет при необходимости анализировать нагрузку на БД и проводить оптимизацию запросов*

### Документирование
- [x] Задокументированы нефункциональные требования к проекту и отдельным его сервисам (количество пользователей/запросов, объемы данных, режимы работы приложений и пр.) \
*На основе этой информации должны приниматься решения об архитектуре приложения, поэтому хорошо чтобы она в явном виде была зафиксирована*

- [x] Имеется документация для подключения к проекту нового разработчика \
*Такая необходимость возникает нередко, поэтому лучше чтобы было с чего начать новому участнику проекта и не требовалось каждому новому участнику передавать знания о проекте устно*

- [x] Задокументирована инфраструктура (сервисы проекта, билды, тестовые стенды) \
*Без этого сложно создавать новые сервисы и/или иным образом менять архитектуру приложения, а также понимать нынешнюю архитектуру приложения и зависимости между его частями*

- [ ] При изменении/добавлении/удалении кода контролируется изменение/добавление сопутствующей документации \
*Могут быть разные варианты реализации подобного контроля: хранение документации в репозитории с кодом и включение ее в PR, обязательное указание ссылки на документацию при завершении задачи в таск трекере и пр.*

- [ ] Задокументирован порядок действий для запуска проекта и/или отдельных его сервисов локально \
*При разработке и отладке без запуска локально как правило не обойтись, а это может быть нетривиальной задачей для сложной системы, поэтому необходимо описание как это сделать*

- [ ] Имеется инструкция по обновлению проекта и/или отдельных его сервисов на тестовых стендах и на проде \
*Обновление это обычно отдельная ответственная задача, требующая от исполнителя повышенной внимательности. Наличие подробной инструкции с описанием шагов и их смысла помогает снизить вероятность ошибки*

### Законность
- [x] У проекта есть лицензия на использование сторонних инструментов
- [ ] При подключении сторонних инструментов соблюдаются требования их лицензий (добавление текста лицензии, упоминание автора и пр.) 
- [x] Архитектура проекта разработана с учетом необходимости соблюдения требований законодательства (ФЗ о персональных данных, обязательное лицензирование отдельных видов деятельности, фискальный учёт, расположение серверов и хранение данных в определённых юрисдикциях) 

### Сопровождаемость
- [ ] На проекте имеется проектная матрица компетенций (механизмы, технологии и инструменты, используемые на проекте и уровни владения ими отдельных членов команды проекта)  \
*Позволяет видеть слабые места в команде проекта и принимать меры по их усилению*

- [ ] Bus factor по компетенциям на проекте >1  \
*Разработка не застопорится при недоступности одного из участников команды*
